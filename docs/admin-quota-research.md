# 后台额度入口调研

## 调研范围

本次需求只落地推广与抽奖后台配置的人民币余额展示与提交转换；充值、赠送、退款、兑换码、用户余额修正等入口保持现状，本文件记录现状与后续建议，不改变这些页面行为。

## 现状盘点

| 入口 | 主要页面/API | 当前单位或数据 | 本次处理 |
| --- | --- | --- | --- |
| 推广比例 | 设置页“推广与抽奖” | 百分比，后端整数基点 | 保持百分比；不属于余额金额转换 |
| 抽奖规则门槛 | `PromotionLotterySetting` / `/api/admin/lottery/settings` | 后端整数 quota | 管理员页面显示 `￥`，提交时按运行时 `quota_per_unit` 转回 quota |
| 抽奖奖品奖励 | `PromotionLotterySetting` / `/api/admin/lottery/prizes` | 后端 `reward_quota` 整数 quota | 管理员页面显示 `￥`，提交时转回 quota |
| 用户充值/钱包 | 钱包、充值与支付设置 | quota 或支付金额，依业务场景不同 | 仅调研，保持现状 |
| 兑换码 | 兑换码管理 | quota 面值 | 仅调研，保持现状 |
| 管理员赠送/余额修正 | 用户管理及钱包管理相关操作 | quota | 仅调研，保持现状 |
| 退款 | 钱包退款及订单处理 | quota 与账本快照 | 仅调研，保持现状 |

## 结论与风险

1. 推广与抽奖奖励最终写入钱包/抽奖账本，内部整数 quota 仍是结算单位；本次只改变管理员输入输出单位，避免浮点金额进入账本。
2. 前端从 `/api/status` 读取运行时 `quota_per_unit`，默认值为 `500000`（1 RMB 对应 500000 quota）。因此不同部署的金额精度会随配置变化。
3. 一个 quota 的默认展示金额为 `￥0.000002`；金额转换使用安全整数校验，空值、负数、非有限数和超安全整数会阻止提交。
4. 其他后台入口若统一改为人民币，需要逐入口确认历史数据、接口契约、最小金额、退款快照和多数据库账本兼容性，建议单独立项并配套迁移/回滚方案。

## 后续建议

- 先为充值、兑换码、赠送、退款、用户余额修正建立统一的金额格式化与 quota 转换 helper，再逐页面迁移。
- API 层继续接收整数 quota，避免改变已有客户端和账本接口；若需要金额 API，建议新增明确的 `amount_rmb` 字段并保留旧字段兼容期。
- 每个入口补充正向、零值、最小单位、超大值、退款幂等和审计日志测试，确认迁移后历史记录仍可追溯。

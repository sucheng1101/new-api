# 推广、抽奖、钱包账务与新版数据看板设计

> 状态：需求已确认，待评审后实施
> 分支：`feature/promotion-system`
> 基线：`dev/skye-v0.13.2-performance`
> 新版数据看板参考提交：`972aed1972820389ea0b603ca58f03f846fbf790`

## 1. 目标

本期在现有 new-api 基础上完成四组互相关联的能力：

1. 两级推广返佣：余额充值或兑换码兑换成功后，直属上级默认获得结算基数的 5%，二级上级默认获得 3%。
2. 三类余额账务：现金余额、赠送余额、推广余额分开核算，消费优先使用赠送余额。
3. 每日消费抽奖：默认当日模型消费满 10 个站点展示金额单位获得一次抽奖机会。
4. 新版概览和数据看板：以指定的官方最新版实现替换当前概览、旧数据看板和运营看板入口。

本设计优先保证账务可追溯、回调幂等、并发一致性，以及 SQLite、MySQL、PostgreSQL 三种数据库兼容。

## 2. 范围边界

### 2.1 本期包含

- 在线余额充值成功后的两级返佣。
- 管理员“充值”操作成功后的两级返佣。
- 兑换码兑换成功后的两级返佣，返佣基数为兑换码面值 quota。
- 推广比例后台配置及订单级比例快照。
- 推广奖励冻结、补发、作废和转入赠送余额。
- 管理员统一额度调整入口：充值、赠送、退款、修正。
- 管理员线下打款后的退款登记与现金余额扣减。
- 现金充值批次按先进先出参与消费和可退款额度计算。
- 抽奖奖池、权重、库存、每日资格、抽奖记录和管理员补发。
- 注册、充值相关 IP 记录及异常提示，不做自动拦截。
- 推广关系、返佣、退款、额度、抽奖的后台查询和审计。
- 新版概览、模型调用分析、调用流向、用户分析。
- 所有新增用户界面的现有多语言适配。

### 2.2 本期不包含

- 用户自主提现或退款入口。
- 自动调用支付平台退款接口。
- 支付平台拒付、撤销或异步退款处理。
- 根据 IP、设备、支付账户自动封禁或拒绝返佣。
- 现金奖品、实物奖品或优惠券奖品。
- 推广奖励直接提现。
- 数据看板 CSV 导出。
- 公开首页推广活动入口。
- 订阅购买、管理员赠送、管理员修正的推广返佣（这些来源固定不参与返佣）。
- 兑换码自动撤销或自动反向追回推广奖励；兑换码退款由管理员账务入口处理。

## 3. 核心术语与金额口径

### 3.1 三类余额

| 账户 | 来源 | 可消费 | 可由管理员退款 | 可直接提现 |
|---|---|---:|---:|---:|
| 现金余额 | 在线充值、管理员充值、兑换码、历史主余额迁移 | 是 | 仅可退款批次 | 否；仅由管理员线下打款后登记扣减 |
| 赠送余额 | 管理员赠送、抽奖奖励、推广余额转入 | 是 | 否 | 否 |
| 推广余额 | 一级/二级返佣、历史邀请余额迁移 | 转入赠送余额后可消费 | 否 | 否 |

用户页面展示：

- 总可用余额：`现金余额 + 赠送余额`。
- 现金余额。
- 赠送余额。
- 推广余额。
- 明确提示赠送余额和推广余额不支持退款或提现。

### 3.2 内部单位

- 余额、返佣、消费门槛和奖品额度均以整数 quota 作为结算单位。
- 前端继续使用现有 quota 转展示金额工具。
- 管理员配置“10”表示站点当前展示金额的 10 个单位，保存时换算为 quota。
- 不使用浮点数完成返佣、退款和抽奖额度结算。

### 3.3 充值金额

- 本期充值支付金额等于到账金额，不设置“支付 100、到账 120”的额外赠送部分。
- 在线支付和管理员充值最终都转换为一个整数 `credited_quota`。
- 推广返佣基数等于该笔成功充值的 `credited_quota`。
- 只有状态首次进入“成功”的充值订单参与返佣。
- 兑换码没有独立支付金额，返佣基数等于兑换成功时该兑换码的面值 quota。
- 订阅支付不进入余额充值结算流程，不产生推广返佣。

## 4. 钱包账务

### 4.1 余额不变量

为兼容现有热路径，保留 `users.quota` 作为总可用余额缓存，同时新增分账户字段：

```text
users.quota = users.cash_quota + users.gift_quota
users.cash_quota >= 0
users.gift_quota >= 0
users.aff_quota >= 0
```

任意余额变更必须在同一数据库事务中同时完成：

1. 更新对应分账户余额。
2. 更新兼容总余额 `quota`。
3. 写入不可变钱包流水。
4. 更新充值批次或消费分摊记录。
5. 提交后更新或失效 Redis 用户额度缓存。

禁止业务代码绕过钱包服务直接修改余额字段。

### 4.2 消费顺序

模型调用最终结算时按以下顺序扣减：

1. 赠送余额。
2. 现金余额。
3. 现金余额内部按充值成功时间、充值记录 ID 先进先出。

预扣、最终结算和退回必须记录来源分摊。一次调用预扣后产生额度返还时，按原分摊来源反向恢复，不能把现金误退成赠送余额，也不能恢复到错误的充值批次。

### 4.3 现金充值批次

每一笔成功充值或兑换码兑换形成一个独立现金批次，至少记录：

- 来源类型和来源记录 ID。
- 初始到账 quota。
- 已消费 quota。
- 已退款本金 quota。
- 剩余可退款 quota。
- 成功时间。

在线充值、管理员充值、兑换码和历史迁移批次都可以作为管理员退款来源，并参与现金余额先进先出消费。

退款必须关联具体成功充值订单、已兑换的兑换码或历史迁移批次，且本次退款本金不得超过该批次剩余可退款 quota，也不得超过用户当前现金余额。

### 4.4 钱包流水

所有钱包变更写入统一不可变流水，至少包含：

- 用户 ID。
- 账户类型：`cash`、`gift`、`promotion`。
- 方向：`credit`、`debit`。
- 变更 quota。
- 变更后账户余额。
- 业务类型。
- 来源类型和来源 ID。
- 幂等键。
- 操作管理员 ID，可空。
- 原因或备注。
- 创建时间。

业务类型至少包含：在线充值、管理员充值、兑换码兑换、管理员赠送、管理员修正、模型消费、模型消费返还、推广返佣、推广转入、抽奖奖励、管理员退款、历史迁移。

## 5. 管理员调整额度

### 5.1 界面

以现有“调整额度”弹窗为基础，移除“覆盖”，调整为四个业务类型：

| 类型 | 操作账户 | 方向 | 产生返佣 | 必填信息 |
|---|---|---:|---:|---|
| 充值 | 现金余额 | 增加 | 是 | 金额、备注；系统生成或填写交易单号 |
| 赠送 | 赠送余额 | 增加 | 否 | 金额、赠送原因 |
| 退款 | 现金余额 | 减少 | 否 | 原充值订单/兑换码记录/历史迁移批次、退款本金、线下打款凭证/单号、原因 |
| 修正 | 现金或赠送余额 | 增加或减少 | 否 | 账户、方向、金额、修正原因 |

不提供任何覆盖余额的接口或界面。

### 5.2 管理员充值

- 每次提交创建一笔独立充值订单。
- 支付金额等于到账金额，只输入一份金额。
- 成功订单增加现金余额并执行两级返佣。
- 同一请求重试由幂等键保护，不能重复入账。
- 不同充值订单独立结算。用户提交 10 笔 100 元订单，其中 8 笔成功，则增加 8 次余额并结算 8 次返佣。

### 5.3 赠送与修正

- 赠送只增加赠送余额，并记录“管理员赠送”。
- 修正可以增加或减少现金余额、赠送余额，但不产生推广返佣。
- 修正减少不能使对应账户或总余额小于零。
- 修正现金余额时必须同步调整可用现金批次。增加现金的修正生成不可退款修正批次；减少现金按先进先出扣减现有现金批次。
- 原因必填，操作管理员、操作前后余额完整记录。

### 5.4 管理员退款

用户先联系管理员，管理员在线下完成实际打款，再在后台登记退款并扣减现金余额。系统不提供用户申请入口，也不调用支付平台接口。

退款必须选择原充值订单、已兑换的兑换码或历史迁移批次。界面展示：

- 原业务类型及初始入账 quota。
- 该订单剩余可退款本金。
- 原一级、二级返佣及状态。
- 累计已退款本金。
- 累计已承担推广成本。
- 本次退款本金。
- 本次推广成本。
- 本次实际线下打款金额。

充值订单和兑换码退款共用以下计算。设：

- `P` 为原充值到账 quota 或兑换码面值 quota。
- `R_total` 为该订单产生的一级、二级返佣 quota 总和。
- `X_after` 为包含本次在内的累计退款本金 quota。
- `C_before` 为此前已计入退款的推广成本 quota。

使用累计法避免多次部分退款产生舍入偏差：

```text
C_after = floor(R_total * X_after / P)
本次推广成本 = C_after - C_before
本次实际线下打款 = 本次退款本金 - 本次推广成本
```

示例：C 充值 100，B 获得 5，A 获得 3。

- 全额退款：C 的现金余额扣减 100，推广成本 8，管理员实际打款 92。
- 先退 50：现金余额扣减 50，推广成本 4，实际打款 46。
- 再退 50：再次扣减 50，再计推广成本 4，再打款 46。

已发放给 A、B 的推广奖励不追回。冻结中的返佣也保留原状态，退款不改变返佣记录；若之后因违规作废，不反向重算已经完成的退款。

退款提交必须包含确认项“线下打款已完成”。系统记录打款单号或凭证文本，但不保存敏感支付凭证原图作为必填项。

## 6. 推广系统

### 6.1 邀请关系

- 注册成功时通过邀请码绑定直属邀请人。
- 用户不能自行修改邀请人。
- 管理员可以修改，必须填写原因并产生审计记录。
- 修改只影响之后成功的充值，历史返佣不重算。
- 禁止邀请自己。
- 禁止形成循环邀请链。
- 返佣最多计算两级。
- 上级不存在时跳过对应层级，不向其他层级递补。

例如 A 邀请 B，B 邀请 C：

- C 的直属上级 B 为一级受益人。
- B 的直属上级 A 为二级受益人。

### 6.2 返佣比例

- 一级默认 5%，即 500 基点。
- 二级默认 3%，即 300 基点。
- 管理员可配置 0% 至 100%。
- 一级与二级合计不得超过 100%。
- 修改只影响修改后首次成功的充值订单。
- 每笔奖励保存比例快照，历史记录不随配置变化。

返佣以整数 quota 逐级向下取整：

```text
一级奖励 = floor(充值 quota * 一级基点 / 10000)
二级奖励 = floor(充值 quota * 二级基点 / 10000)
```

计算结果小于 1 quota 时不生成余额，但订单结算记录需保留“舍入为零”的结果用于审计。

### 6.3 充值结算时机与幂等

- 充值订单状态首次从非成功进入成功时立即结算。
- 只接受最终成功状态，不处理支付平台后续撤销、拒付或异步退款。
- 每个 `充值订单 + 受益层级` 只能存在一条返佣记录。
- 支付回调重试、管理员重复点击和服务重启不能重复加款或返佣。
- 余额入账、返佣记录和订单推广结算状态必须在同一事务中完成。

### 6.4 兑换码返佣与退款

- 兑换码兑换成功后，兑换码面值进入现金余额，并生成可退款现金批次。
- 兑换码面值 quota 即返佣基数，使用兑换时生效的一级、二级比例。
- 受益人、比例、面值和奖励金额保存快照，后续修改邀请关系或比例不影响历史结果。
- 每个 `兑换码记录 + 受益层级` 只能存在一条返佣记录。
- 无效、禁用、过期或已使用的兑换码不增加余额，也不产生返佣。
- 同一兑换码的并发兑换只允许一次成功；现金入账、兑换码状态和两级返佣在同一事务中提交。
- 兑换码支持管理员退款，退款本金不能超过该兑换码批次的剩余可退款 quota。
- 兑换码退款使用与充值相同的累计推广成本公式：扣减兑换用户现金余额，已发给上级的返佣不追回，推广成本从本次实际线下退款金额中扣除。
- 部分退款、现金余额不足、已消费额度和重复提交的处理规则与充值退款一致。
- 兑换码退款后保持已使用状态，已退款额度不能再次兑换。
- 订阅购买成功不调用推广结算服务。

### 6.5 奖励状态

推广奖励状态：

- `credited`：已计入推广余额。
- `frozen`：受益人被封禁，等待管理员处理。
- `voided`：管理员确认违规后作废。
- `rounded_zero`：计算结果不足 1 quota。

若 B 被封禁而 A 正常：

- B 的一级奖励进入 `frozen`。
- A 的二级奖励正常进入 `credited`。
- B 解封后，管理员可补发冻结奖励。
- 确认违规后，管理员可作废冻结奖励。
- 已经转入赠送余额并消费的历史奖励不追缴。

### 6.6 推广余额转入

- 用户可将推广余额按 1:1 转入赠送余额。
- 无手续费、无最低金额、不过期。
- 转入后不能转回推广余额。
- 转入后的资金仍不可退款或提现。
- 每次转入写入独立转入记录和双边钱包流水。
- 请求使用幂等键并在事务内校验推广余额，防止并发超额转入。

### 6.7 推广页面

钱包页不再承载邀请奖励卡片。新增独立推广页面，展示：

- 邀请链接、邀请码和复制操作。
- 当前一级、二级比例。
- 一级、二级有效邀请人数。
- 当前推广余额、累计奖励、累计已转入。
- 奖励流水及状态。
- 下级用户脱敏列表。
- 推广余额转入赠送余额操作。

下级列表只展示脱敏用户名、注册时间、邀请层级和累计贡献奖励，不展示余额、具体消费明细或充值原金额。

## 7. IP 记录与异常提示

### 7.1 记录点

- 注册请求 IP。
- 绑定邀请关系时的注册 IP。
- 创建充值订单 IP。
- 支付成功回调沿用订单创建 IP，不信任回调服务器 IP 作为用户 IP。
- 管理员充值记录管理员 ID 和后台请求 IP。

IP 获取必须使用项目已配置的可信代理规则，不能直接信任任意客户端传入的转发头。

### 7.2 异常提示

以下情况生成风险提示：

- 邀请人与被邀请人注册 IP 相同。
- 同一 IP 短时间注册多个存在上下级关系的账户。
- 同一 IP 为多个下级创建充值订单。
- 其他可由后台规则识别的高频邀请或充值行为。

风险记录只用于后台标签、筛选和人工判断：

- 不阻止注册。
- 不阻止充值。
- 不自动冻结用户。
- 不自动取消返佣。

## 8. 抽奖系统

### 8.1 入口

- 抽奖组件放在钱包管理页面原“邀请奖励”区域。
- 邀请奖励从钱包页面移除并迁移至独立推广页面。
- 用户端展示可用次数、奖池、抽奖按钮、结果和最近中奖记录。

### 8.2 获得次数

- 默认当日模型调用最终实际消费达到 10 个站点展示金额单位，获得 1 次抽奖机会。
- 只统计模型调用最终结算的净消费 quota。
- 不统计充值、订阅购买、兑换码、管理员加款、管理员赠送或余额转移。
- 默认每日最多获得 1 次，消费 20 或 30 仍只获得 1 次。
- 门槛和每日最多次数由管理员配置，为后续扩展多次保留数据结构。
- 日界线使用系统配置时区，默认 `Asia/Shanghai`。

资格发放发生在模型调用最终结算后。同一请求重试只能累计一次消费；预扣金额不能直接计入，必须以最终扣费为准。

### 8.3 跨天规则

后台提供“允许跨天保留”开关：

- 默认关闭：当日未使用次数在次日零点失效。
- 开启：未使用次数长期累计，直到使用。
- 无论开关状态如何，每日消费进度均在日界线后重新统计。

实现上使用带业务日期和失效状态的资格记录，通过请求时惰性失效配合后台任务清理；不能只依赖恰好在零点执行的单一任务。

### 8.4 奖品配置

第一期奖项类型仅包含：

- 赠送额度。
- 未中奖。

奖品字段：名称、类型、赠送 quota、整数权重、库存、无限库存标记、单用户每日中奖上限、启用状态、生效时间、失效时间、排序、说明。

- 后台使用权重配置并显示换算后的当前实际概率。
- 用户端展示奖品内容，不展示精确概率。
- 库存为零的有限库存奖品自动退出有效奖池。
- 未中奖作为特殊奖项参与权重计算。
- 至少存在一个有效奖项；若奖池无有效项，抽奖接口返回业务错误且不消耗次数。

### 8.5 抽奖执行

- 使用服务端密码学安全随机数进行加权选择。
- 一次抽奖在事务内锁定或条件扣减资格和库存。
- 每次抽奖保存奖池版本、候选奖项、权重、计算概率、结果和请求幂等键快照。
- 抽中额度后立即进入赠送余额并写入钱包流水。
- 抽中未中奖只记录结果。
- 网络重试返回原抽奖结果，不能再次消耗次数或重复发奖。

### 8.6 管理员能力

- 配置消费门槛、每日次数上限、跨天保留开关和系统时区。
- 新增、编辑、启停和排序奖品。
- 查看资格获得、过期和使用记录。
- 查看抽奖记录与概率快照。
- 对异常订单手动补发抽奖赠送额度，补发进入赠送余额并记录管理员与原因。

`users` 新增：

`redemptions` 扩展：

- `wallet_transactions`：统一不可变钱包流水。

### 9.3 新增推广表

- `promotion_rewards`：来源类型、来源 ID、充值或兑换用户、受益用户、层级、比例快照、基数、奖励、状态。
- `promotion_transfers`：推广余额转入赠送余额记录。
- `invitation_relation_audits`：管理员修改邀请关系前后值及原因。
- `promotion_risk_events`：IP 异常类型、关联用户/订单、证据摘要、处理状态。

关键唯一约束：

- `promotion_rewards(source_type, source_id, level)`。
- `promotion_transfers(idempotency_key)`。
- `wallet_transactions(idempotency_key)`。
- 充值业务的渠道交易号继续保持现有唯一性要求。

### 9.4 新增抽奖表

- `lottery_prizes`：奖项配置、权重、库存和生效范围。
- `lottery_daily_progress`：用户、业务日期、净消费、已授予次数、已使用次数。
- `lottery_chances`：资格来源、获得日期、过期时间、状态。
- `lottery_draws`：请求幂等键、奖池快照、结果、奖品和发奖流水关联。

关键唯一约束：

- `lottery_daily_progress(user_id, business_date)`。
- `lottery_draws(idempotency_key)`。
- 模型消费累计使用现有请求唯一标识防止重复计入。

### 9.5 字段与数据库兼容要求

- JSON 快照使用 `TEXT` 保存，并通过 `common.*` JSON 包装函数读写。
- 业务布尔值采用项目兼容写法，不依赖单一数据库的布尔 SQL 字面量。
- 不使用 PostgreSQL JSONB 运算符、MySQL 专属聚合函数或 SQLite 不支持的列修改。
- 金额字段使用整数类型；时间使用现有 Unix 时间风格。
- 高频列表和结算键增加普通或复合索引，但迁移必须兼容三种数据库。

## 10. 服务边界与事务

新增或抽取以下服务：

- `WalletService`：三账户变更、现金批次、消费分摊、流水和缓存一致性。
- `TopUpSettlementService`：统一承接所有支付渠道和管理员充值成功事件。
- `PromotionService`：邀请链解析、比例快照、返佣、冻结和转入。
- `RedemptionSettlementService`：在兑换事务内完成兑换码现金入账和推广结算。
- `RefundService`：退款可用额、推广成本累计算法和管理员单据。
- `LotteryService`：每日消费累计、资格、抽奖和发奖。

所有充值成功入口必须调用同一个结算服务，禁止在 EPay、Stripe、Creem、Waffo 等控制器中分别复制返佣逻辑。充值与兑换码共用 `PromotionService` 的返佣计算和幂等规则。

外部回调采用短事务：验证回调后，以订单 ID 或交易号锁定订单，检查状态，完成余额与返佣写入并提交。通知、日志等非关键操作在提交后执行。

## 15. 迁移方案

### 15.1 用户余额

上线迁移时：

- 现有 `users.quota` 全部迁移为 `cash_quota`。
- `gift_quota` 初始化为 0。
- 现有 `aff_quota` 继续作为推广余额。
- 现有 `aff_history` 继续作为历史累计推广奖励。
- 为现有 `quota` 建立一笔“历史现金余额迁移”合成充值批次和汇总流水。该批次推广成本为 0，管理员核实后可将其作为退款来源。
- 为现有 `aff_quota` 建立一笔“历史推广余额迁移”流水。

历史主余额统一视为现金余额，以免损害老用户权益。

### 15.2 历史推广

- 保留现有邀请关系。
- 上线前充值不补算一级或二级返佣。
- 历史奖励没有逐笔来源时只生成迁移汇总，不伪造充值订单关联。

### 15.3 数据看板

- 为 `quota_data` 添加新维度字段和索引。
- 历史行的新维度使用默认空值或 0。
- 新代码部署后只对新调用写入完整流向维度。

### 15.4 部署顺序

1. 备份数据库并验证恢复方式。
2. 增加可空或有默认值的新字段与新表。
3. 分批回填用户余额和迁移流水。
4. 校验 `quota = cash_quota + gift_quota`。
5. 部署兼容新旧字段的后端。
6. 部署新版前端。
7. 观察账务、回调和额度缓存一致性。
8. 稳定后再清理旧页面和确认废弃接口。

迁移需可重入，并用迁移版本或唯一幂等键防止重复生成历史流水。

## 16. 一致性、并发与故障处理

- 所有余额写入均通过数据库事务。
- 使用可移植的行锁或带余额条件的原子更新，不能只依赖进程内互斥锁。
- Redis 只作为额度缓存，不作为账务事实来源。
- 数据库提交成功但缓存更新失败时，立即失效缓存并记录告警。
- 支付回调、推广转入、管理员调整、退款和抽奖均使用唯一幂等键。
- 并发消费不能使任何余额或现金批次小于零。
- 并发抽奖不能超发有限库存。
- 服务在事务提交前崩溃时不产生部分入账；提交后重试返回已有结果。

## 17. 测试要求

### 17.1 钱包与消费

- 赠送余额足够、部分足够和为零时的消费顺序。

- 无邀请人、只有一级、完整两级三种邀请链。

- 10 笔订单 8 笔成功只结算 8 笔。
- 同一订单回调多次只增加一次现金余额和一次各层奖励。

- 兑换码按面值执行全额或部分退款，并按兑换时保存的返佣快照计算推广成本。
- 已消费本金、现金余额不足、订单剩余不足时拒绝。
- 兑换码退款后保持已使用状态，不能再次兑换。

## 18. 验收标准

1. 任意用户都能清楚看到现金、赠送、推广三类余额及总可用余额。
2. 模型消费始终优先使用赠送余额，再按先进先出使用现金充值批次。
3. 每笔成功充值或兑换码只结算一次返佣，一级默认 5%、二级默认 3%。
4. 失败充值和失败兑换不增加余额、不产生返佣；多笔成功业务分别结算。
5. 推广余额只能转为赠送余额，转入后仍不可退款或提现。
6. 管理员可以完成充值、赠送、退款和修正，且不存在覆盖余额操作。
7. 退款只由管理员在线下打款后登记，系统正确扣减本金并显示推广成本和实际打款金额。
8. 被封禁受益人的奖励冻结，上上级正常奖励不受影响。
9. IP 异常在后台可见，但不会触发自动风控。
10. 用户每日消费达到配置门槛后获得抽奖次数，默认每日一次且零点失效。
11. 抽奖结果可审计、重试不重复扣次数、额度奖品只进入赠送余额。
12. 独立推广页面、钱包抽奖区域和管理员后台在桌面与移动端可正常使用。
13. `/console` 使用新版概览，模型、流向、用户分析按角色正确展示，旧运营看板不再出现在导航。
14. 历史余额和邀请关系迁移后总额不减少，历史充值不补算返佣。
15. 所有账务流水、管理员操作和配置变更均可查询并能关联到来源业务单据。

## 19. 已确认决策摘要

- 充值返佣基数为成功充值到账金额，支付金额等于到账金额。
- 兑换码参与返佣，返佣基数为兑换码面值；兑换余额进入可退款现金批次。
- 兑换码退款规则与充值一致，已发放推广奖励不追回，推广成本由兑换用户承担。
- 订阅购买不产生推广返佣。
- 一级默认 5%，二级默认 3%，后台可修改。
- 返佣立即到账；封禁用户的奖励进入冻结。
- 退款不追回上级奖励，由充值用户承担相应推广成本。
- 不处理支付平台拒付、撤销或异步退款。
- 管理员加款区分充值、赠送和修正；取消覆盖。
- 用户不具有自主退款或提现入口。
- 推广余额转赠送余额，不可提现，消费优先使用赠送余额。
- 抽奖默认每日消费满 10 获得一次，默认不跨天保留。
- 抽奖第一期只有赠送额度和未中奖。
- IP 只记录并提示异常，不执行自动风控。
- 公开首页不增加推广入口。
- 新版概览和数据看板替换旧实现，不提供 CSV 导出。
